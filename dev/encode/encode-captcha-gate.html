ENCODE CAPTCHA gate

ENCODE fronts www.encodeproject.org with an AWS WAF that inspects the Origin of every request. Approved origins (https://igv.org, https://aidenlab.org, …) are served. Everything else that looks like a real browser gets a CAPTCHA challenge, returned with the misleading status 405 Method Not Allowed and the header x-amzn-waf-action: captcha.

localhost is not on the approved list and never will be, so no ENCODE-hosted track can be loaded by any igv.js-based app running locally. This page reproduces that.

This page is currently served from origin .

Expected result when served from localhost: the control fetch succeeds, the ENCODE fetches fail, and the ENCODE tracks below never draw while the genome, refseq annotations, and the non-ENCODE bigWig do. Served from https://igv.org, everything succeeds — that asymmetry is the whole bug.

Note that the challenge response is readable from page JavaScript: measured against the live host it carries access-control-allow-origin: * and, better still, access-control-expose-headers: x-amzn-waf-action. So a fetch here can read both the 405 and the header naming the real cause — this is not a CORS failure, and the information needed to report "the provider blocked us" instead of "405" is available in the browser.
